Cloud agent assign fails with “GitHub rate limited — user quota is full”? Skip the assign.

AI-written, and it says so · Checked against the Cursor forum thread and docs: August 2026 · Nothing on this page is for sale

TL;DR. The toast is not about your GitHub account’s quota — the limit sits on Cursor’s side of the GitHub integration, and Cursor staff say fixes are in the pipeline. What works today: skip the assign. Start the cloud agent yourself from cursor.com/agents or the IDE, pointed at the same repo, and paste the issue — title, full body, the comments that settled decisions — into the first message. Paste the Ticket, the free formatter on this site, turns a ticket into that message. Don’t type “fix #25” and expect the agent to fetch it: even when assign works, the agent VM’s token often can’t read issues.

The symptom

You assign a Cursor cloud agent to a GitHub issue — or ask a bot chat to launch one — and instead of an agent you get a toast:

GitHub rate limited: GitHub is rate limiting requests.
Please try again later.

Some hit the same wall worded as “user quota is full”; from a Grok Bot chat it comes back as “Could not launch the cloud agent: GitHub is rate limiting requests.” — one sentence, no status code, no headers, no agent.

The confusing part, documented by the reporters on the public forum thread: your GitHub account is fine. They checked api.github.com/rate_limit and saw roughly 5,000 of 5,000 requests remaining, gh could read the private repo and the issue, and both the GitHub and Cursor status pages were green. Waiting three-plus hours didn’t clear it. Reconnecting GitHub under Cursor Dashboard → Integrations didn’t either.

Whose rate limit it actually is

Sticking to what the thread and the docs actually establish:

  • Not your personal token. Reporters’ own API quota was nearly untouched while assign kept failing, so waiting for “your” limit to reset waits on the wrong thing.
  • The assign path runs through Cursor’s GitHub App. Assigning an agent to an issue (or launching one via bot or API) has to resolve the repo and issue through Cursor’s GitHub integration — not through your gh login. Cursor’s own Cloud Agents API docs mark the repo-listing endpoint on that path with “very strict rate limits”: 1 request per user per minute, 30 per hour. That fits what one reporter observed — listing cloud agents worked while every launch failed.
  • Cursor has confirmed it’s on their side. Staff (Colin) replied on the thread that they’re “aware of some GitHub rate limiting issues (not specific to your configuration)” and, a day later, that “a few fixes are in the pipeline.” That was August 19, 2026. No date was given, and this page won’t invent one — the thread is where the fix will be announced.

The practical consequence: you can’t fix this from your side of the integration, and retrying assign in a loop pushes against per-user-per-minute caps — it can only make the window worse. What you can do is route around the assign entirely.

The workaround: skip the assign

Step 1 — start the agent from the web or IDE, not from the issue

Open cursor.com/agents (or the cloud agent panel in the Cursor IDE), pick the same repo, and start an agent with a written first message. You’re no longer going through the issue-assign flow that’s throwing the toast — the agent boots, clones the repo, and works branches and pull requests as usual.

Step 2 — paste the ticket, don’t reference it

Resist writing “fix #25” and calling it done. That hands the agent a pointer instead of a ticket, and there’s a second, older failure waiting behind this one: even when assign works, the token the agent’s VM receives often lacks issues scope, so gh issue view 25 comes back 403 and the agent works from the title and its own assumptions. (That failure has its own guide.) Paste the ticket itself:

  • the title and the full body, not a summary,
  • acceptance criteria, expected vs. actual,
  • the comments that settled decisions (“we agreed to gate this behind a flag”),
  • links to related PRs and files.
Work the ticket below. Open a PR when done — do not merge it.
If anything is ambiguous, say so in the PR description instead
of deciding.

--- TICKET #25: [title pasted here] ---
[full issue body pasted here]

--- COMMENTS THAT SETTLED DECISIONS ---
[the comments that changed the spec, pasted here]
You don’t have to format that by hand. Paste the Ticket — a free tool on this site — takes the title, body, comments, and done-condition and emits a complete first message with the guardrails already written: new branch, this ticket only, tests, a PR, never a merge. No account, no backend; nothing you type leaves the page.

Step 3 — optional, for teams: one GH_TOKEN so agents can fetch issues themselves

If pasting every ticket gets old, give the agent VMs a credential that can read issues — once, for the whole team, instead of one personal token per person:

  • Create one fine-grained personal access token (from a service account if you have one): repository access limited to the repos agents work in, permissions Issues: read-only plus the Metadata read GitHub adds automatically. No write scopes.
  • Add it in the Cursor dashboard under Cloud Agents → Secrets, named GH_TOKEN. Secrets are injected as environment variables, and the gh CLI picks GH_TOKEN up on its own. It reaches agents started after you save it.
  • Keep it out of the repo — not committed in .cursor/environment.json, not in a pushed .env, never pasted into a prompt.

The click-by-click version, including how to verify the token before trusting it, is in the issues-scope guide. Note what this does and doesn’t solve: it lets a running agent fetch the ticket; the assign button itself stays broken until Cursor ships their fix.

What doesn’t fix it

  • Waiting out your own quota. It was never spent — reporters waited hours with a full quota and got the same toast.
  • Reconnecting the GitHub integration. Tried on the thread, from the dashboard, more than once. The error came back.
  • Hammering the assign button. The documented caps on Cursor’s GitHub App path are per user, per minute and per hour. A retry loop spends them faster.

FAQ

Is my GitHub account actually rate limited?

Almost certainly not, but check in one request: open api.github.com/rate_limit while signed in, or run gh api rate_limit. Reporters on the thread saw 4,988–5,000 of 5,000 remaining while assign failed. If your quota genuinely is exhausted, you have a different problem than this page covers.

When will assign work again?

Cursor staff said on August 19, 2026 that “a few fixes are in the pipeline and will be deployed shortly.” No date was promised, so this page doesn’t promise one either. Watch the forum thread — updates land there.

Do agents started this way still branch and open PRs?

Yes. The failure happens while resolving the repo and issue during assign, before any agent exists. An agent you launch from the web or IDE clones the repo, works on a branch, and opens a pull request as usual — and a human on your team still reviews and merges every PR.

Once Cursor ships the fix, is the paste habit wasted?

No. Assign has a second, unrelated gap: the token the agent VM receives often can’t read issues even when assign itself succeeds, so “fix #25” still starves the run of the acceptance criteria and the decision comments. Pasting the full ticket — or setting up the team GH_TOKEN — stays the reliable way to get the whole spec into the agent. The issues-scope guide covers both.

If the agent starts but still can’t read the ticket

That’s the adjacent failure, and it has its own page: Your Cursor cloud agent can’t read GitHub issues — the two fixes that work. Between the two — launch directly, paste the ticket, one read-only team token in secrets — a rate-limited assign button stops being the thing that blocks your day.
